# 그래프 모델 재현 평가

작성: 반서윤 · 작성일: 2026-10-04
대상: 태영 선배님 그래프 모델 `code.zip` (GNN + 그래프 통계 트리 모델 + 앙상블)

## 요약

- 그래프 모델 코드를 **수정 없이** 공식 확장 대회 환경과 다른 운영체제(Windows)에서 다시 학습했다.
- **최종 앙상블 Macro F1은 0.50997**로 원래 결과 0.50950과 0.0005 차이였고, 같은 비율(GNN 25% + ExtraTrees 37.5% + HGB 37.5%)이 선택되었다.
- **같은 환경에서 2번 실행하면 트리와 GNN 모두 소수점 끝자리까지 동일**했다. 원래 결과와의 차이(GNN 단독 −0.0159)는 주로 **운영체제 차이**에서 온다(스레드 수만 바꾸면 최대 0.003, 같은 스레드 수에서 운영체제가 다르면 최대 0.016).
- 기존 평가 코드로 채점한 결과가 원래 코드의 계산과 일치하므로 기존 8개 모델과 **같은 기준으로 비교**할 수 있다. 기존 최고(CatBoost 0.2568) 대비 약 2배이며, 향상의 대부분은 **그래프 통계 특징**에서 나왔다(트리 블렌드 0.5007, GNN 추가 효과 +0.009).
- 1차에서 문제였던 **3.x 샌드위치 계열의 혼동은 대부분 해결**되었지만, 같은 대분류 안의 혼동(1.20 → 1.10, 3.10 → 3.30, 2.30 → 2.40)은 오히려 늘었다.
- 제출 묶음 크기 **152.1MB**(500MB 한도의 30%), 평가 데이터 기준 추론 시간 **약 71초**(10분 한도의 12%)로 한도 안이다.
- **전체 데이터 재학습 시 GNN 에포크 수가 검증 최고 에포크로 정해져**, 같은 코드여도 환경에 따라 최종 모델이 다르게 만들어진다(원래 12에포크, 재실행 6에포크).

## 1. 실행 조건

| 항목 | 내용 |
|---|---|
| 코드 | 전달받은 `code.zip` 그대로 (수정 없음) |
| 환경 | Python 3.12.14, `requirements-competition.lock.txt` (공식 확장 대회 환경), Windows |
| 데이터 | main 브랜치 (데이터는 `797d114`와 동일. 이후 커밋은 문서·코드 추가만), fit 17,238 / validation 4,307 |
| 실행 단계 | `prepare → trees → gnn(--epochs 12 --hidden 32) → select_model`, 이후 `refit-trees → refit-gnn → package_model → predict` |
| CPU | `OMP_NUM_THREADS=2`, GNN `--threads 2`(원래 3). ExtraTrees는 코드에 `n_jobs=4`로 고정되어 그대로 둠 |
| 평가 | 검증 확률을 `id, y_true, y_pred`로 변환(`select_model.py`와 같은 계산)한 뒤 `scripts/model/evaluate_models.py --predictions`로 채점 |
| 반복 | 같은 조건에서 `trees`, `gnn`을 2회 실행. 원인 확인용으로 GNN을 `--threads 3`으로 1회 추가 실행 |

패키지 비교: 코드의 `requirements.lock.txt` 25개 패키지가 모두 공식 확장 환경에 있다. torch 2.14.1, scikit-learn 1.9.1, numpy·pandas·scipy·networkx 버전이 같다. 다른 것은 torch 보조 패키지 3개(filelock 4.0.10 → 4.0.9, fsspec 2026.9.0 → 2026.6.0, MarkupSafe 3.0.4 → 3.0.3)로 계산에는 영향이 없다.

### 앙상블 비율별 비교 (GNN 비중)

| GNN 비중 | 원래 | 재실행 |
|---:|---:|---:|
| 0% | 0.50029 | 0.50072 |
| **25%** | **0.50950** | **0.50997** |
| 50% | 0.50719 | 0.50992 |
| 75% | 0.48741 | 0.48594 |

두 환경 모두 25%가 선택되었고 트리 비율도 같은 50:50이었다. 다만 재실행에서는 25%와 50%가 **0.00005 차이로 사실상 동점**이었다. 25%가 특별한 최적값이라기보다 **25~50% 구간이 비슷하다**고 보는 것이 정확하다. 앙상블은 GNN 비중이 25%라 GNN의 환경별 차이가 대부분 상쇄되어 GNN 단독보다 안정적이었다.

## 3. 같은 기준 비교 (기존 모델 포함)

모든 수치는 `evaluate_models.py`로 같은 검증 데이터(4,307건)에서 계산했다.

| 그래프 트리 블렌드 (50:50) | 그래프 통계 | 0.5007 | 0.6241 | 0.6287 | 0.4946 | **0.5383** | 0.4946 |

관찰:

- **성능 향상의 대부분은 특징에서 나왔다.** 31개 특징의 트리 모델(0.22~0.26)에서 그래프 통계 특징의 트리 모델(0.46~0.50)로 거의 2배가 되었다. GNN을 더한 추가 향상은 +0.009다. 1차 결과에서 "모델을 바꿔도 0.24 근처에 머무는 것은 특징의 한계"라고 본 해석과 일치한다.
- **GNN은 재현율 쪽, 트리는 정밀도 쪽 모델이다.** GNN 단독은 Balanced Accuracy(0.526)가 가장 높지만 Macro Precision(0.439)이 낮다. 트리와 섞으면 정밀도가 0.53으로 올라 Macro F1이 높아진다.
- Weighted F1 − Macro F1 차이는 그래프 모델 모두 0.115~0.126으로, 기존 모델과 비슷하게 큰 클래스를 더 잘 맞힌다.

## 6. 시간과 크기

### 학습 시간 (Windows, CPU 2스레드)

| 단계 | 시간 | 측정 |
|---|---:|---|
| prepare (그래프 생성) | 미측정 | |
| trees (LR + ExtraTrees + HGB 학습·검증) | **2분 43초 ± 4초** | 2회 |
| gnn (12에포크) | **14분 53초 ± 1분 18초** | 2회 |
| select_model | 11초 | 1회 |
| refit-trees (전체 데이터) | 3분 43초 | 1회 |

GNN은 결과가 동일한데도 시간 차이가 2분 가까이 났다. 참고로 기존 8개 모델 평가 전체(3회 반복)는 8분 45초였다.

| 평가 데이터 5,387건 (비례 환산) | **약 71초** |

## 7. 전체 데이터 재학습의 GNN 에포크

`train.py` 130~131번 줄에서 `refit-gnn`은 `--epochs` 값 대신 **검증 단계에서 저장된 최고 모델의 에포크 수**만큼 학습한다. 학습률 스케줄은 원래 에포크 수(12) 기준이다.

| | 검증 최고 에포크 | 최종 GNN 학습 에포크 |
|---|---:|---:|
| 원래 (macOS) | 12 | 12 |
| 재실행 (Windows) | 6 | 6 (스케줄 중간에서 종료) |

같은 코드·seed여도 환경에 따른 검증 점수의 작은 차이가 최고 에포크 선택을 바꾸고, 최종 제출 모델의 학습 길이까지 달라진다. 재현 심사에서 학습 코드를 다시 돌릴 때 고려해야 할 부분이다.

## 8. 서버 제출 호환성

유저 제출 구조(`train.py`, `inference.py`, `requirements.txt`, `model/`)와 비교한 결과다. 실제 서버 오류 원인은 웹 쪽 로그로 확인해야 한다.

| 항목 | 유저 제출 구조 / LR 베이스라인 | 그래프 모델 |
|---|---|---|
| 학습 코드 | `train.py` | `train.py` (있음) |
| 추론 진입점 | `inference.py` | `predict.py` |
| 실행 인자 | `--input --output` | `--model --run --input --structures --output` |
| 입력 | 특징 CSV | 서열 CSV + 구조 ZIP |
| 모델 위치 | `model/` | `runs/main/` |
| 의존성 파일 | `requirements.txt` | `requirements.lock.txt` |
| 추론 필요 패키지 | scikit-learn (경량 환경에 있음) | PyTorch (확장 환경에만 있음) |
| 크기 / 추론 시간 | 0.01MB / 1초 미만 | 152.1MB / 약 71초 |

서버가 경량 추론 환경(`requirements-inference.lock.txt`)으로 실행된다면 PyTorch가 없어 GNN을 불러올 수 없다. 서버가 구조 ZIP을 입력으로 넘기는지, 진입점 이름과 모델 위치를 무엇으로 찾는지도 확인이 필요하다.

## 9. 해석 시 주의사항

- **검증 데이터로 고른 값이 두 가지 있다.** 앙상블 비율과 GNN 에포크를 같은 검증셋으로 골랐으므로 점수는 낙관적일 수 있다.
- 단일 분할 결과다. 같은 환경 반복은 2회이며, 시간 표준편차는 2회 기준이다.
- 추론 시간은 내 컴퓨터(CPU 2스레드) 기준이며 서버 CPU에 따라 달라질 수 있다. 5,387건 시간은 비례 환산값이다.

## 10. 검토할 사항

- 앙상블 비율을 25%로 고정할지, 25~50% 구간이 비슷하다는 점을 반영할지
- GNN을 포함할지: +0.009 향상 대비 CPU 학습 약 15분, PyTorch 의존, 환경에 따라 최대 약 0.02 변동
- 재현 심사 허용 오차(팀 문서 Q11): 같은 환경에서는 완전 재현되지만, 운영체제가 다르면 같은 스레드 수에서도 GNN이 최대 0.016 달라지므로, 심사 시 운영체제·실행 이미지·스레드 수를 참가자 환경과 같게 고정하는 방안
- 전체 재학습 에포크를 검증 최고 에포크가 아닌 고정값으로 할지
- 서버 제출 형식(진입점, 구조 입력, 실행 환경)을 그래프 모델에 맞출 방법
- 약한 클래스(2.170, 3.90, 3.50, 4.10)와 같은 대분류 안의 혼동 개선 방향
